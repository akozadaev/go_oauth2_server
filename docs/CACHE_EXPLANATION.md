# Объяснение работы In-Memory кеша клиентов

## Для чего был нужен кеш?

In-memory кеш был предназначен для **ускорения доступа к данным клиентов** путем уменьшения количества запросов к базе данных.

### Проблема без кеша:
- Каждый раз при валидации OAuth2 клиента (например, при запросе токена) нужно было делать запрос к PostgreSQL
- Запросы к БД медленнее, чем чтение из памяти (RAM)
- При высокой нагрузке это создавало дополнительную нагрузку на БД

### Решение с кешем:
- Данные клиентов сохранялись в памяти (в `map[string]oauth2.ClientInfo`)
- При повторных запросах данные читались из памяти, минуя БД
- Это значительно ускоряло работу для часто используемых клиентов

## Как работал кеш?

### 1. Структура данных

```go
type ClientStore struct {
	db      *sql.DB
	clients map[string]oauth2.ClientInfo  // Кеш: client_id -> ClientInfo
	logger  *slog.Logger
}
```

### 2. Алгоритм работы при получении клиента

```go
func (cs *ClientStore) GetByID(ctx context.Context, id string) (oauth2.ClientInfo, error) {
	// ШАГ 1: Проверка кеша (быстро, в памяти)
	if cs.clients != nil {
		if client, exists := cs.clients[id]; exists {
			// ✅ Нашли в кеше - возвращаем сразу (0 мс, без обращения к БД)
			return client, nil
		}
	}

	// ШАГ 2: Если не в кеше - запрос к БД (медленно, ~1-5 мс)
	client := &oauthModels.Client{}
	query := `SELECT id, secret, domain, user_id FROM clients WHERE id = $1`
	err := cs.db.QueryRowContext(ctx, query, id).Scan(...)
	
	// ❌ Проблема: данные из БД НЕ сохранялись обратно в кеш!
	// Поэтому каждый раз при отсутствии в кеше нужно было идти в БД
	return client, nil
}
```

### 3. Пополнение кеша

Кеш заполнялся только при создании нового клиента:

```go
// В PostgresStore.CreateClient()
func (s *PostgresStore) CreateClient(ctx context.Context, client *models.Client) error {
	// 1. Сохраняем в БД
	_, err := s.db.ExecContext(ctx, query, ...)
	
	// 2. Сохраняем в кеш
	clientInfo := &oauthModels.Client{...}
	if cs, ok := s.clientStore.(*ClientStore); ok {
		cs.Set(ctx, client.ID, clientInfo)  // ← Пополнение кеша
	}
}

func (cs *ClientStore) Set(ctx context.Context, id string, client oauth2.ClientInfo) error {
	if cs.clients == nil {
		cs.clients = make(map[string]oauth2.ClientInfo)  // Инициализация при первом вызове
	}
	cs.clients[id] = client  // Сохранение в кеш
	return nil
}
```

## Пример работы

### Сценарий 1: Первый запрос (cold cache)

```
1. Запрос: GetByID("client-123")
   ↓
2. Кеш пуст (cs.clients == nil)
   ↓
3. Запрос к PostgreSQL: SELECT * FROM clients WHERE id = 'client-123'
   ↓
4. Время: ~2-5 мс
   ↓
5. Возврат данных клиента
   ❌ НО данные НЕ сохранились в кеш!
```

### Сценарий 2: Повторный запрос (если кеш был заполнен при создании)

```
1. Запрос: GetByID("client-123")
   ↓
2. Проверка кеша: cs.clients["client-123"] - найдено!
   ↓
3. Время: ~0.001 мс (чтение из RAM)
   ↓
4. Возврат данных из кеша (без обращения к БД)
   ✅ Быстро!
```

### Сценарий 3: Клиент создан до запуска сервера

```
1. Сервер запускается
   ↓
2. Кеш пуст (cs.clients == nil)
   ↓
3. Запрос: GetByID("old-client-456")
   ↓
4. Кеш пуст → запрос к БД
   ↓
5. Данные получены, но НЕ сохранены в кеш
   ↓
6. Следующий запрос того же клиента → снова запрос к БД!
   ❌ Кеш не работает для существующих клиентов!
```

## Проблемы реализации

### 1. **Кеш не заполнялся автоматически**

Кеш заполнялся только при вызове `Set()`, который вызывался только при создании нового клиента. Если клиент уже существовал в БД, он никогда не попадал в кеш.

**Решение:** Нужно было сохранять данные в кеш после запроса к БД:
```go
func (cs *ClientStore) GetByID(...) {
    // ... запрос к БД ...
    cs.clients[id] = client  // ← Этого не было!
    return client, nil
}
```

### 2. **Кеш не синхронизирован между экземплярами**

При горизонтальном масштабировании:

```
Экземпляр 1:         Экземпляр 2:         Экземпляр 3:
┌─────────────┐      ┌─────────────┐      ┌─────────────┐
│ clients: {} │      │ clients: {} │      │ clients: {} │
│ map (пустой)│      │ map (пустой)│      │ map (пустой)│
└─────────────┘      └─────────────┐      └─────────────┘
      ↓                    ↓                    ↓
   PostgreSQL ←───────────┴────────────────────┘
   (общая БД)

Проблема: если клиент создан через экземпляр 1, 
он попадет только в кеш экземпляра 1.
Экземпляры 2 и 3 не будут знать о нем до обращения к БД.
```

### 3. **Нет механизма инвалидации**

Если клиент был изменен в БД (например, изменен secret), кеш не обновлялся автоматически. Экземпляр продолжал использовать старые данные из кеша.

### 4. **Нет TTL (Time To Live)**

Кеш хранился бесконечно, пока не перезапустится сервер. Это могло привести к устаревшим данным.

## Почему это было проблемой для масштабирования?

### Проблема консистентности данных

```
Время T0: Клиент создан через экземпляр 1
  → БД: client-123 добавлен
  → Кеш экземпляра 1: client-123 сохранен ✅

Время T1: Запрос приходит на экземпляр 2
  → Кеш экземпляра 2: пуст
  → Запрос к БД: client-123 найден ✅
  → НО: client-123 НЕ сохранился в кеш экземпляра 2 ❌

Время T2: Запрос приходит снова на экземпляр 2
  → Кеш экземпляра 2: все еще пуст
  → Снова запрос к БД ❌ (нет ускорения)

Время T3: Клиент изменен в БД (secret изменен)
  → БД: client-123 обновлен ✅
  → Кеш экземпляра 1: содержит старые данные ❌
  → Кеш экземпляра 2: пуст (не проблема, но нет кеша)
```

## Преимущества текущего решения (без кеша)

### ✅ Консистентность данных
- Всегда актуальные данные из БД
- Нет проблем с устаревшим кешем

### ✅ Простота
- Нет сложной логики синхронизации
- Меньше кода для поддержки

### ✅ Масштабируемость
- Все экземпляры работают одинаково
- Нет проблем с распределенным кешем

### ⚠️ Производительность
- Поиск по PRIMARY KEY очень быстрый (~1-2 мс)
- PostgreSQL имеет свой внутренний кеш (shared_buffers)
- При наличии connection pooling это достаточно быстро

## Когда кеш был бы полезен?

Кеш был бы полезен, если бы:
1. **Автоматически заполнялся** при первом запросе
2. **Имел TTL** для обновления данных
3. **Был распределенным** (Redis) для синхронизации между экземплярами
4. **Имел механизм инвалидации** при изменении данных

## Альтернативное решение с Redis

Для дальнейшей оптимизации можно использовать Redis:

```go
type RedisClientStore struct {
	db     *sql.DB
	redis  *redis.Client
	logger *slog.Logger
}

func (cs *RedisClientStore) GetByID(ctx context.Context, id string) (oauth2.ClientInfo, error) {
	// 1. Проверяем Redis (быстро, распределенный)
	client, err := cs.redis.Get(ctx, "client:"+id).Result()
	if err == nil {
		return parseClient(client), nil  // ✅ Из кеша
	}
	
	// 2. Если не в Redis - запрос к БД
	clientInfo := cs.getFromDB(ctx, id)
	
	// 3. Сохраняем в Redis на 1 час
	cs.redis.Set(ctx, "client:"+id, serialize(clientInfo), time.Hour)
	
	return clientInfo, nil
}
```

Преимущества Redis:
- ✅ Распределенный кеш (все экземпляры видят одни данные)
- ✅ TTL (автоматическое обновление)
- ✅ Инвалидация (можно удалить ключ при изменении)
- ✅ Быстрее БД (~0.5-1 мс vs ~1-5 мс)

## Выводы

1. **Кеш был нужен** для ускорения доступа к данным клиентов
2. **Реализация была неполной** - кеш не заполнялся автоматически при чтении
3. **Проблема масштабирования** - каждый экземпляр имел свой кеш
4. **Текущее решение (без кеша)** проще и надежнее для масштабирования
5. **Для дальнейшей оптимизации** можно использовать Redis с TTL и инвалидацией
