# Анализ производительности и масштабируемости OAuth2 Server

## Текущее состояние

### ✅ Сильные стороны

1. **Stateless архитектура**
   - Хранилище токенов использует PostgreSQL (stateless)
   - JWT токены stateless по своей природе
   - Нет shared state между экземплярами для токенов

2. **Индексы в БД**
   - Индексы на `access_token`, `refresh_token`, `client_id`, `user_id` в таблице `oauth2_tokens`
   - Индекс на `access_expires_at` для быстрого поиска активных токенов

3. **Мониторинг**
   - Prometheus метрики для отслеживания производительности
   - Логирование запросов

4. **Таймауты**
   - Настроены таймауты для HTTP сервера (ReadTimeout, WriteTimeout, IdleTimeout)
   - Таймауты для запросов к БД в production token store

### ⚠️ Проблемы и ограничения

#### 1. **Connection Pooling не настроен**
**Проблема:** Используется стандартный `database/sql` пул без настройки параметров.
- По умолчанию: `MaxOpenConns = 0` (без ограничений), `MaxIdleConns = 2`
- При высокой нагрузке это может привести к исчерпанию соединений с БД

**Рекомендация:** Настроить connection pooling:
```go
db.SetMaxOpenConns(25)              // Максимум открытых соединений
db.SetMaxIdleConns(5)               // Максимум idle соединений
db.SetConnMaxLifetime(5 * time.Minute) // Максимальное время жизни соединения
```

#### 2. **In-memory кеш клиентов не синхронизирован**
**Проблема:** `ClientStore` использует in-memory кеш (`map[string]oauth2.ClientInfo`), который не синхронизирован между экземплярами.
- При горизонтальном масштабировании каждый экземпляр имеет свой кеш
- Изменения клиентов не распространяются между экземплярами
- Нет механизма инвалидации кеша

**Рекомендация:** 
- Использовать Redis для распределенного кеширования клиентов
- Или убрать кеш и всегда обращаться к БД (при наличии индексов это будет достаточно быстро)

#### 3. **Отсутствие индекса на username**
**Проблема:** Таблица `users` не имеет индекса на поле `username`.
- `ValidateUser` делает `SELECT ... WHERE username = $1` без индекса
- При большом количестве пользователей это замедлит валидацию

**Рекомендация:** Добавить индекс:
```sql
CREATE INDEX IF NOT EXISTS idx_users_username ON users(username);
```

#### 4. **Нет кеширования для валидации пользователей**
**Проблема:** Каждый запрос валидации пользователя идет в БД.
- `bcrypt.CompareHashAndPassword` - CPU-intensive операция
- При высокой нагрузке это может стать узким местом

**Рекомендация:** 
- Использовать Redis для кеширования результатов валидации (с TTL)
- Или использовать rate limiting для предотвращения брутфорса

#### 5. **Нет connection pooling для PostgreSQL в URL**
**Проблема:** В `DATABASE_URL` не указаны параметры пула соединений.

**Рекомендация:** Добавить параметры в connection string:
```
postgres://user:pass@host:port/db?sslmode=disable&pool_max_conns=25&pool_min_conns=5
```

#### 6. **Отсутствие rate limiting на уровне приложения**
**Проблема:** Rate limiting есть только в nginx, но не в самом приложении.
- При прямом доступе к серверу (минуя nginx) нет защиты от DDoS

**Рекомендация:** Добавить middleware для rate limiting (например, `github.com/didip/tollbooth`)

## Ответы на вопросы

### 1. Может ли проект работать под высокой нагрузкой?

**Частично.** Проект имеет хорошую основу для работы под нагрузкой, но есть несколько критических проблем:
- ✅ Stateless архитектура (JWT токены)
- ✅ Индексы в БД
- ⚠️ Не настроен connection pooling
- ⚠️ In-memory кеш клиентов не масштабируется
- ⚠️ Нет индекса на username

**Ожидаемая производительность:**
- **Без оптимизаций:** ~500-1000 RPS (зависит от железа)
- **С оптимизациями:** ~5000-10000 RPS

### 2. Можно ли запустить с балансировщиком в нескольких экземплярах?

**Да, но с ограничениями.**

**✅ Что работает:**
- Токены хранятся в PostgreSQL (stateless)
- JWT токены можно валидировать без обращения к БД
- Обработка запросов stateless

**⚠️ Проблемы:**
- In-memory кеш клиентов не синхронизирован между экземплярами
- При изменении клиента нужно перезапустить все экземпляры или подождать TTL кеша

**Рекомендация для масштабирования:**
1. Использовать Redis для кеширования клиентов
2. Или убрать кеш и всегда обращаться к БД (при наличии индексов)
3. Использовать sticky sessions не требуется (stateless)

### 3. Как можно ускорить проект?

#### Приоритет 1: Критические оптимизации

1. **Настроить Connection Pooling**
   ```go
   // В main.go после sql.Open
   db.SetMaxOpenConns(25)
   db.SetMaxIdleConns(5)
   db.SetConnMaxLifetime(5 * time.Minute)
   ```

2. **Добавить индекс на username**
   ```sql
   CREATE INDEX IF NOT EXISTS idx_users_username ON users(username);
   ```

3. **Убрать или исправить in-memory кеш клиентов**
   - Вариант А: Убрать кеш, всегда обращаться к БД
   - Вариант Б: Использовать Redis для распределенного кеша

#### Приоритет 2: Важные оптимизации

4. **Добавить Redis для кеширования**
   - Кеш клиентов
   - Кеш результатов валидации пользователей (с TTL)
   - Rate limiting

5. **Оптимизировать запросы к БД**
   - Использовать prepared statements где возможно
   - Добавить connection pooling параметры в DATABASE_URL

6. **Добавить rate limiting на уровне приложения**
   ```go
   // Использовать github.com/didip/tollbooth
   limiter := tollbooth.NewLimiter(10, nil) // 10 req/sec
   ```

#### Приоритет 3: Дополнительные оптимизации

7. **Использовать connection pooling на стороне PostgreSQL**
   - PgBouncer для connection pooling
   - Настроить `max_connections` в PostgreSQL

8. **Оптимизировать логирование**
   - Использовать уровни логирования (debug только в dev)
   - Асинхронное логирование для production

9. **Добавить мониторинг производительности**
   - Отслеживать время выполнения запросов
   - Алерты на медленные запросы

10. **Использовать read replicas для чтения**
    - Настроить read replicas PostgreSQL
    - Читать клиентов и пользователей с реплик

## Рекомендуемая архитектура для продакшена

```
Load Balancer (nginx/HAProxy)
    ↓
Multiple OAuth2 Server Instances (3-5)
    ↓
Redis Cluster (для кеширования)
    ↓
PostgreSQL Primary (запись)
    ↓
PostgreSQL Replicas (чтение)
```

## Пример конфигурации для высоких нагрузок

### Docker Compose с масштабированием

```yaml
services:
  oauth2-server:
    build: .
    deploy:
      replicas: 3
    environment:
      - DATABASE_URL=postgres://...
      - REDIS_URL=redis://redis:6379
    depends_on:
      - postgres
      - redis

  redis:
    image: redis:7-alpine
    command: redis-server --maxmemory 256mb --maxmemory-policy allkeys-lru

  postgres:
    image: postgres:16-alpine
    command: postgres -c max_connections=200 -c shared_buffers=256MB
```

### Nginx upstream с несколькими экземплярами

```nginx
upstream oauth2_backend {
    least_conn;  # Балансировка по наименьшему количеству соединений
    server oauth2-server-1:8080;
    server oauth2-server-2:8080;
    server oauth2-server-3:8080;
}
```

## Метрики для мониторинга

1. **HTTP метрики:**
   - `http_requests_total` - общее количество запросов
   - `http_request_duration_seconds` - время выполнения запросов

2. **Database метрики:**
   - Количество открытых соединений
   - Время выполнения запросов
   - Количество ошибок подключения

3. **OAuth2 метрики:**
   - `oauth2_tokens_issued_total` - количество выданных токенов
   - `oauth2_tokens_validated_total` - количество валидированных токенов

4. **Системные метрики:**
   - CPU usage
   - Memory usage
   - Goroutine count
